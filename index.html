Abstract

Embedded C correctness depends on the hardware the code drives — registers, interrupts, DMA and timing — which software-level test harnesses never exercise. This systematic review synthesises how large language models are used for hardware-aware test generation in embedded C across nine research questions, joining two literatures that have not met: non-LLM firmware re-hosting and fuzzing, and LLM-driven test generation. Reported in PRISMA 2020 format without a compliance claim, the review is unregistered and documents no bibliographic database search; 105 registered records yielded 59 exclusions and 46 inclusions, collapsing to 28 unique studies (29 reports), of which 13 LLM-construct studies denominates every LLM-population statement. Each question was answered from its own verified dataset (N = 4–8; the derived gap analysis, N = 6); no quality-assessment instrument was applied and quantitative meta-analysis is impossible on the source evidence. Test types are bimodal — unit 2/4, HIL/system-level 2/4, integration and regression 0/4 — and only 1/4 emits C test code. Zero-shot prompting (6/7), retrieval-augmented generation (5/7) and agentic workflows (4/7) dominate, but eleven hardware-specification categories are each 0/8 as model input. Dependency handling is delegated, not generated (5/6; behaviourally faithful doubles 0 of 27 configurations); LLM-driven interrupt/timing test generation is 0/6; execution is emulator-bound (6/6; real hardware primary 0/6); loops close universally (5/5) on software signals; and real hardware, HIL, fault seeding, fault exposure and human evaluation are each 0/4, as are common benchmark, baseline, quantified metric and evaluation environment. Fourteen of the 28 pairwise study-set overlaps are zero: no study is simultaneously LLM-based, test-generating, embedded-C-source-level and hardware-aware. Author-acknowledged gaps are strongest for hardware-free validation (5/6), narrow advisory LLM capability (5/6) and peripheral dependence (4/6). Every zero is bounded to the verified dataset and licenses no prevalence claim; the structure indicates a pre-paradigm intersection, not a failing literature.

1. Introduction

Embedded software — the C and C++ code that runs on microcontrollers and firmware and interacts directly with sensors, actuators, buses, device registers, interrupts and direct-memory-access (DMA) channels — is foundational to safety-critical and resource-constrained systems, from automotive electronic control units to industrial controllers. Testing such code is harder than testing general-purpose software because correctness is entangled with the hardware it drives: a peripheral-dependent routine may compile and pass an isolated unit test yet misbehave once it touches a device register, an interrupt line or a DMA buffer, and asynchronous interrupts and timing constraints can alter behaviour in ways that a purely software-level test harness never exercises. These are not incidental edge cases but the core difficulty that embedded testing must confront, and they are exactly the properties that make hardware awareness central rather than peripheral to the problem.

Because that entanglement is so fundamental, a body of systems and security research has made the hardware abstraction itself a research object in order to test embedded code without complete physical hardware. Firmware re-hosting and fuzzing frameworks model peripheral interfaces and memory-mapped I/O explicitly — P2IM through automatic peripheral-interface modelling [13], HALucinator through abstraction-layer emulation [14], Fuzzware through precise MMIO modelling [15], and DICE through automatic emulation of DMA input channels [16] — while a parallel line of work treats interrupts and asynchronous events as first-order obstacles, modelling interrupt service routines and interrupt-driven state changes to make firmware behaviour observable (IEmu [10], AIM [12], AidFuzzer [9]). This literature establishes the hardware-modelling problems concretely, but it is largely infrastructure research that predates, and is independent of, the recent rise of large language models (LLMs).

LLMs have meanwhile become a mainstream engine for automated test generation and code synthesis across software engineering, as documented in broad surveys of software testing with LLMs [21]. Within the embedded domain specifically, the studies reviewed here show LLMs being applied to concrete testing tasks rather than generic code generation: retrieval-augmented generation of unit tests for industrial embedded C (EmbC-Test [1]); a structured multi-agent workflow producing unit tests with library-aware doubles and iterative repair for firmware (openSIL [2]); requirement-driven functional-test generation for ECUs executed on hardware-in-the-loop benches (AutoHIL [3]); execution-path-aware prompting for embedded C/C++ test-case generation (Tran [4]); continual pre-training or retrieval enhancement aimed at low-level embedded code (H2LooP [6], Smarter-not-Bigger [5]); and agentic embedded-IoT development with compile/flash feedback (EmbedGenius [7]). Related work sits adjacent to test generation rather than squarely within it — agent-driven validation and patching of LLM-generated embedded firmware (Abtahi & Azim [8]), comparative evaluation of LLMs on C test-case generation (Guzu et al. [19]), and benchmarking or characterisation studies that assess many models on embedded development and debugging tasks (EmbedAgent [20], Englhardt et al. [11]). Of these, Guzu et al. [19] and the broad survey of software testing with LLMs [21] are not members of the reviewed corpus: [19] does not appear in the 105-record screening register at all, having entered the project through a separate dataset, and [21] enters only as one of the six RQ9 evidence studies. Neither is counted toward the 28 included studies, the 46 records, the 29 reports or any cohort denominator, and both are listed separately in Part B of the References. A recurring mechanism across the test-generation efforts is an iterative generate–execute–refine loop, mirroring general test-generation systems that close the loop using compiler errors, coverage, runtime traces or execution results (CoverUp [17], Panta [18], LLMLOOP [22]). Across all of these, it is important not to conflate producing a test artefact with demonstrating that the artefact compiles, executes, or is behaviourally correct on hardware; the studies differ sharply on how much of that chain they actually report.

What has received comparatively little attention, on the evidence of the studies this review covers, is a synthesis that treats the two strands above together — LLM-driven test generation and the embedded-C-specific dimensions that make it distinctive: peripheral and hardware-configuration dependencies, hardware/software context supplied to the model, interrupt and asynchronous/timing behaviour, the execution and validation environment, feedback loops, and evaluation. The reviewed corpus divides these concerns along the very lines that general software-testing surveys and firmware re-hosting infrastructure leave unaddressed in combination: the broad testing-with-LLMs survey carries essentially no embedded-hardware dimension [21], the re-hosting work is not LLM-based [9][13][16], and the emerging LLM test-generation studies each engage only part of the peripheral / interrupt / execution-validation picture [1][2][3][8]. Whether these dimensions are converging into a coherent, hardware-aware capability for embedded-C test generation, or are being pursued by largely separate groups, is precisely the kind of question that an integrated, evidence-traceable review is positioned to examine. This review's contribution is therefore one of scope and analytical framing rather than a claim of bibliographic priority.

Synthesising both the context provided to the model and the environment where generated tests are compiled, executed or validated matters because the two jointly bound how much hardware-awareness a result can carry. On the context side, whether an LLM is given datasheet, register or peripheral specifications, and interrupt or timing constraints — versus what is merely discussed in the paper — bears directly on whether a generated test can encode hardware-specific behaviour. On the validation side, the execution setting (emulator, virtualised real-time system, hardware-in-the-loop bench or physical device) determines which hardware behaviours a test can evidence at all; producing an artefact and demonstrating that it passes on real hardware are different levels of evidence, and conflating them would overstate a result's hardware validity. Examining these dimensions as named, separable concerns — rather than folding them into a generic "code quality" account — is therefore central to judging how hardware-aware LLM test generation for embedded C actually is.

To examine this systematically, the review addresses nine research questions, using the approved wording recorded in the project. RQ1–RQ8 are treated as primary empirical dimensions, each answered from its own verified dataset; RQ9 synthesises the evidence and explicitly reported limitations into research gaps and future directions, and is reported with its own distinct denominators.

  • RQ1. What types of tests for embedded C software (unit, integration, hardware-in-the-loop, regression) are generated or supported by LLM-based approaches?
  • RQ2. Which LLMs and which prompting or adaptation strategies (zero/few-shot, RAG, fine-tuning, agentic workflows) are used for embedded test generation?
  • RQ3. What hardware/software context (datasheets, register maps, HAL/driver code, specifications) is provided to LLMs for test generation?
  • RQ4. How do LLM-based approaches handle hardware and peripheral dependencies (mocks, stubs, fakes, simulators)?
  • RQ5. How do existing approaches address interrupts, asynchronous behavior, and timing constraints?
  • RQ6. In what environments (emulators, simulators, virtual platforms, real hardware, HIL) are generated tests executed and validated?
  • RQ7. What feedback loops (compiler errors, coverage, runtime traces, execution results) are used to refine generated tests?
  • RQ8. What metrics and validation methods (compilability, pass rate, coverage, mutation score, fault detection, human evaluation) are used to evaluate generated tests?

First, it provides a structured synthesis of LLM-based test-generation approaches relevant to embedded C, organised around the nine questions above. 2. Background and Related Concepts

This section defines the vocabulary and the counting conventions on which every count in Section 4 depends. It introduces no new evidence, no new studies and no new citations beyond those already listed in the References; its purpose is to make the review's classification lens explicit before results are reported against it, because — as Section 7 documents — several of this review's zero counts are sensitive to the definitions given here.

2.1 Why hardware awareness is a distinct problem in embedded C testing

Embedded C code is not self-contained. It reads and writes memory-mapped device registers, configures and services interrupt lines, moves data through direct-memory-access (DMA) channels, and observes or produces signals on buses and pins under timing constraints that the compiler does not model. Two consequences follow for testing, and both recur throughout the results reported in Section 4.

First, correctness is entangled with the substrate. A routine that compiles and passes an isolated unit test may still misbehave once it touches a peripheral register, an interrupt vector or a DMA descriptor, because the behaviour under test is defined jointly by the C source and by hardware semantics that the source only references. A test that never instantiates those semantics can pass without exercising them.

Second, the cost of exercising real hardware is high, which has produced a substantial literature on testing firmware without complete physical devices. That literature treats the hardware abstraction itself as the research object: peripheral interfaces and memory-mapped I/O are modelled explicitly so that firmware can be executed off-target, and interrupt service routines and interrupt-driven state changes are modelled so that asynchronous firmware behaviour becomes observable at all. Within this review's corpus, that work forms the Contextual non-LLM infrastructure cohort (§2.4) — P2IM [13], HALucinator [14], Fuzzware [15], DICE [16], IEmu [10], AIM [12] and AidFuzzer [9] — and it is, by construction, not LLM-based.

Large language models (LLMs) have meanwhile become a mainstream engine for automated test generation and code synthesis across software engineering [21], and a body of work now applies them to embedded tasks specifically: retrieval-augmented generation of unit tests for industrial embedded C (EmbC-Test [1]), multi-agent unit-test generation with library-aware doubles and iterative repair for firmware (openSIL [2]), requirement-driven functional-test generation for electronic control units executed on hardware-in-the-loop benches (AutoHIL [3]), execution-path-aware prompting for embedded C/C++ test-case generation [4], low-level-code adaptation through continual pre-training or retrieval enhancement [5][6], and agentic embedded-IoT development with compile/flash feedback (EmbedGenius [7]).

These two bodies of work address complementary halves of the same problem, and the central analytical observation of this review — developed in §5.1 and §4.9.4 — is that within the verified corpus they do not meet inside any single study.

2.2 Constructs examined by this review, and how each is operationalised

Each research question corresponds to a named construct. Because the primary studies use these terms inconsistently (documented in §7.3), the operationalisation below is stated once and applied uniformly.

Test types (RQ1). The four canonical levels named in the review question: unit, integration, hardware-in-the-loop (HIL) and regression. A further distinction is preserved between a test type an approach generates and one it merely supports; in this corpus every reported type is of the generated kind. Output language (C, Python, JSON or another artefact form) is recorded separately, because a test expressed in Python or JSON is not a C test artefact even when its target is C code.

Models and adaptation strategies (RQ2). Zero-shot and few-shot prompting, retrieval-augmented generation (RAG), fine-tuning (recorded separately for the generation model and for any auxiliary component such as an embedding model), and agentic workflows — multi-step pipelines in which a model plans, invokes tools and revises. Strategies co-occur within a study, so counts overlap by design and do not sum to the denominator.

Hardware and software context supplied to the model (RQ3). The critical distinction here is between material provided to the model and material merely discussed in the paper. Only the former counts. Within it, this review separates software context (source files, repository structure, build logs, dependency lists, existing tests) from hardware context (datasheets, register maps, microcontroller or processor specifications, clock and memory-map configuration, board and electrical-interface documentation, sensor/actuator and communication-protocol specifications, interrupt, timer and DMA specifications, and HAL/driver/BSP/RTOS artefacts). A further distinction separates inference-time context from training-time consolidation: a corpus of datasheets absorbed into weights during pre-training or continual pre-training is not context supplied at generation time, and is not counted as such.

Peripheral and hardware-dependency handling (RQ4). Handling divides into two families that this review keeps apart. The provision family creates substitutes — test doubles such as mocks, stubs and fakes, or generated peripheral models, device drivers, HAL layers, wrappers and link-time replacements. The replacement family swaps the execution substrate — an emulator, simulator or physical target replaces the absent hardware. A hybrid strategy uses both. Note that the term "mock" is used with two different senses in this literature: as a unit-test double, and as a verb denoting system-level state simulation; the two are not merged. A test double is counted as behaviourally faithful only where register, timing, interrupt or protocol semantics are modelled, and faithfulness is treated as a separate question from whether faithfulness was ever measured.

Interrupts, asynchronous behaviour and timing (RQ5). Three levels are distinguished: the presence of interrupts in the target; the modelling of interrupt behaviour (interrupt service routine handling, interrupt injection, nested-interrupt and priority semantics, interrupt-controller simulation); and the testing of temporal properties (worst-case execution time, jitter, deadline validation, race conditions, delay duration, periodic execution, timeout as a functional constraint). Time control — a fake or mock clock, a deterministic simulation-time mechanism, explicit clock-domain modelling — is recorded separately from time inheritance, in which virtual time exists only as a side effect of running an emulator. Concurrency counts are reported alongside, because an absence of operating-system-level scheduling semantics is not an absence of concurrency handling.

Execution and validation environments (RQ6). Five environment classes are recognised: emulator, simulator (strict sense), virtual platform, hardware-in-the-loop rig and real hardware. Two further distinctions matter. A real target may serve as the primary execution environment or only in a secondary role such as confirming a bug found off-target or providing a baseline for comparison; the two are counted separately. And the emulator/simulator boundary is a classification decision, not an empirical fact: the same tooling may be coded on either side depending on the lens applied, which is why this review reports the conflict rather than resolving it (§7.3).

Feedback loops (RQ7). A loop is closed when generated artefacts are refined using signals returned from processing them, and one-shot when they are not. Feedback sources are recorded individually: compiler errors, compiler warnings, coverage, runtime traces, static-analysis findings, execution results, test failures, hardware or peripheral feedback, mutation or fault information, human feedback, and model self-critique. Evaluation-only measurement is not a refinement input and is not counted as a loop. Loop frequency is never treated as evidence of loop effectiveness.

Evaluation metrics and validation methods (RQ8). Validation methods (execution, compilation, coverage analysis, mutation testing, simulation or emulation, benchmark comparison, fault seeding, fault exposure, human evaluation, expert review, qualitative and static analysis) are recorded separately from headline metric names (coverage, mutation score, pass rate, pass@k), because a shared metric name does not imply a shared definition or denominator. Comparability is itself a measured property: whether studies share a benchmark, a baseline, a quantified metric or an evaluation environment.

2.3 Counting units: records, reports and studies

This review distinguishes three counting layers, and conflating them is the single most common source of error in the underlying project records. A record is one row of the screening register; a study entered for several research questions appears as several records. A report is one published or deposited document; one study may have several reports, as when a conference version and a preprint both exist. A study is one unit of scientific work. The verified values for this corpus are 46 records, 29 reports and 28 studies, and each is used only where its own layer is meant (§3.6).

A related distinction runs through every count in Section 4: a study is not a configuration. Several research questions are extracted at configuration level — an experimental setting, a model variant or a prompt condition within one study — and configuration-level counts (51 for RQ2, 32 for RQ3, 27 for RQ4, 24 for RQ5, 11 for RQ6, 25 for RQ7, 46 for RQ8) are never presented as study prevalences.

2.4 Cohorts and why they are demarcated rather than merged

Not every included study belongs to the population about which the review's headline question is asked. Eligibility adjudication therefore demarcated four cohorts rather than excluding studies whose LLM relevance failed, so that no verified evidence was discarded while no non-LLM study could inflate an LLM statistic. The LLM-construct cohort (13 studies) is the population for every LLM-population statement, so its denominator is 13 and never 28. The Contextual non-LLM infrastructure cohort (8 studies) contributes environment and mechanism framing for RQ4–RQ6 only. The general-SE comparator cohort (4 studies) calibrates RQ7/RQ8 mechanisms but is not counted as an embedded-C finding. The grey-zone cohort (3 studies, one of whose identity is unresolved in the records) is retained verbatim with flags. Cohort definitions, membership and counting rules are given in full in Table 3 (§3.6).

Each research question additionally reports over its own verified dataset, whose study membership and denominator are registered in Table 4 (§4.0). Percentages are therefore valid only inside their own denominator and are never pooled, averaged or summed across research questions.

2.5 Evidence-status vocabulary

Three vocabularies are used throughout Section 4 and are defined here once.

Reporting status. "Not reported" (the source is silent), "Unclear" (the source addresses the point but does not settle it) and "No" (the source states a negative) are kept distinct and are never collapsed into one another. In particular, a silence is never converted into a negative.

Two kinds of zero. A type I zero answers "did any verified study use method X?" with no. It supports an underexplored-within-this-dataset claim. A type II zero answers "did any study discuss Y as a limitation?" with no. It is silence about a topic, not absence of the topic, and it licenses no gap claim whatsoever. The same construct can be a type I zero in one dataset and a type II zero in another — HIL, HAL and RTOS behaviour are exactly such cases — and the two readings are never substituted for one another (Table 5, §4.9.3).

Evidence grades for gap statements. EA = an author-acknowledged limitation confirmed by the verification record; EA-q = acknowledged but downgraded during verification; SI = synthesis-inferred from adjacent evidence; IFS = inferred from silence; NE = not established (type II); NR = outside the study's stated scope. Single-study items are marked as such and are not inflated into field-level gaps.

2.6 What this section does not do

This section defines terms; it does not survey the field and does not substitute for the systematic evidence reported in Section 4. No claim about the prevalence, effectiveness or maturity of any technique is made here, and none of the counts above is a finding. Section 3 documents how the corpus was assembled and what its documentation limits are; Section 4 reports the verified counts; Sections 5–7 interpret them and bound them.

3.1 Review protocol and research questions

The review addresses nine questions. RQ1–RQ8 are answered from eight independently compiled, record-level datasets; RQ9 is a derived question synthesised over the RQ1–RQ8 corpora (it introduces no new studies):

5. Discussion

Reading conventions. Three rules from Section 4 carry over verbatim to every statement below. First, observations and interpretations are kept distinct: reported counts, verbatim source statements and per-study attributions are observations; analytical readings are flagged as interpretations and are never attributed to the primary studies. Second, every percentage holds only within its own dataset denominator (RQ1 = 4, RQ2 = 7, RQ3 = 8, RQ4 = 6, RQ5 = 6, RQ6 = 6, RQ7 = 5, RQ8 = 4; RQ9 = 6 studies at study level, never the 75 retained limitation instances); no percentage is pooled, averaged or summed across datasets. Third, a zero count means "not reported within the verified dataset under our classification lens", never "absent from the literature"; and zeros at the method-use level (type I) are distinguished throughout from zeros at the limitation-discussion level (type II), which may not be converted into gap claims. Because 14 of the 28 pairwise study-set overlaps are zero (§4.9.4), any statement linking two RQ dimensions for which no study carries both measurements is a structural contrast between disjoint populations, not a paired finding; no association, correlation or causal claim is made anywhere in this section unless it rests on within-study co-occurrence.

5.1 The organising finding: a research question without a fully instantiated study

The most consequential observation in this review is about the shape of the evidence itself. The verified dataset contains no study that is simultaneously LLM-based, test-generating, embedded-C-source-level and hardware-aware (RQ9 construct-validity statement, confirmed independently by all six RQ9 verification files). The 27 identifiable studies across the eight empirical datasets split into two almost-disconnected clusters (revised cross-RQ synthesis §1.4): cluster A (test/code generation and automotive system-level work, 12 studies, populating RQ1–RQ4) and cluster B (firmware fuzzing, re-hosting and general-purpose test generation, 15 studies, populating RQ4–RQ8). Strategy and context evidence (RQ2, RQ3) shares no study with interrupt, environment, feedback and metric evidence (RQ5–RQ8); the only documented bridge between the clusters runs through Abtahi & Azim (S13) via a feature-level identity match (M2) that remains pending author verification (§4.11, note N6). If that match is rejected, the RQ4×RQ5/RQ6/RQ7 overlaps drop to zero and the two clusters become fully disjoint bodies of evidence.

Interpretation. We read this structure — following the cross-RQ synthesis (I9) — as characteristic of a pre-paradigm stage of a cross-cutting topic, not as a failure of the literature: the four elements of the review's core construct are being worked on, productively but separately, by two research communities that publish in different venues and evaluate against different criteria (the domain split recorded in RQ7, where embedded-firmware studies emphasise runtime/hardware-adjacent feedback while general-purpose test-generation studies emphasise coverage, compilation and mutation feedback, is consistent with this reading). The immediate analytic consequence is that every "relationship among dimensions" discussed below is constrained by the evidence structure: the strongest statements available are (a) exhaustive within-dataset counts, (b) directionally convergent patterns across disjoint datasets, and (c) author-acknowledged limitations at the study level. None of these licenses a causal claim.

5.2 Test types, LLM strategies and context: what the paired evidence shows

The one well-paired relationship. RQ2 × RQ3 (6 studies, title-level matches; S02 EmbC-Test, S05 openSIL, S06 EmbedAgent, S07 Smarter-not-Bigger, S08 H2LooP, S09 EmbedGenius) is the only candidate relationship with adequate same-study pairing (observed). Within it, the pattern is consistent and specific. Retrieval-augmented generation is common (5/7 in RQ2; 3/8 on RQ3's narrower inference-time criterion — the two codings are kept unmerged per §4.11 note N5), but what is retrieved is exclusively software artefacts: legacy tests, repository structure, build logs, dependency lists, library-usage rules, known-good #include directives; no study retrieves a datasheet, register map or hardware specification document (RQ3, verbatim). Register maps, MCU/processor specifications, board documentation, clock/memory-map/timer/DMA/interrupt/protocol/sensor-actuator specifications and inference-time HAL/driver/BSP/RTOS artefacts are each 0/8; datasheet+RAG, register map+HAL and HAL+driver+peripheral-specification combinations are each 0. Among the studies whose LLM role is genuinely test generation (S02, S05, S12), confirmed hardware context is 0/3. Context richness does not track strategy complexity: the richest hardware context in the dataset (S06: the only confirmed peripheral specification, plus board, pinout, schematic) coexists with a mid-complexity stack, while the only study supplying datasheets at inference time (S08 H2LooP) does so via training-time weight consolidation — the source records the 117-vendor pretraining corpus as "training-time, not inference-time context" — and performs code completion, not test generation.

Interpretation. In this dataset, "hardware awareness" is operationalised almost entirely as software artefacts plus execution feedback — RQ3's own phrase is that execution feedback (compiler errors, build/flash logs, coverage, HIL action results, present as context in 4/8 studies) is treated as a stand-in for hardware awareness. The strategic machinery of the field (RAG, agentic loops, tool pipelines) is being spent on the software side of that boundary. Whether the substitution works is exactly what the validation and metric datasets cannot answer (5.6–5.8), because no study carrying context evidence also carries execution-environment or metric evidence.

Test types × strategies: not assessable. RQ1 × RQ2 shares a single study (S02, which is a unit-test generator using RAG-grounded structured prompting on host-side artefacts). The RQ1 distribution is strictly bimodal — Unit 2/4, HIL 2/4, Integration 0/4, Regression 0/4 — and the two HIL studies (2511.19132v1; AutoHIL, 3832155) carry no strategy records at all, while the only HIL-adjacent study in RQ2 (S07) was coded as test support, not generation, and RQ1 records LLM support activity as "never directed at the authoring of a non-unit, non-HIL test type". No mapping between test type and strategy can be claimed (observation about the evidence structure). The two 0/4 test types must also be read differently (per §4.1): Integration's zero is an evidence void — two explicit scope exclusions that ceded integration to established SIL/MIL/PIL toolchains — whereas Regression's zero is total silence (no explicit "No" anywhere), supporting neither capability nor incapability.

5.3 Dependency handling meets the execution environment: an empty intersection

Three datasets describe the same boundary from disjoint vantage points (all observations).

  • RQ4 (dependencies, n = 6). In 5/6 studies the LLM produces no dependency-handling artefact; handling is delegated outward to existing platforms (Wokwi, QEMU plus the official FreeRTOS port), an industrial virtual-vehicle system, an author-built HIL testbench or physical boards. The one unambiguous positive cell is LLM-generated tests plus stubs (S05, host execution); mocks are "Partially / Not established". Every combination of LLM-generated artefacts with hardware-relevant execution — tests with simulators, emulators, HIL or real hardware; LLM-built peripheral models, device drivers, HALs, wrappers, configured execution environments; test doubles combined with simulation/emulation/physical execution — is 0 studies. Behaviourally faithful doubles (register, timing, interrupt, protocol semantics) are 0/27 configurations, and quantitative fidelity assessment of virtual environments against real hardware is likewise 0 ("No study measures how closely its virtual environment matches real hardware"). The replacement and provision families "never intersect"; hybrid/layered strategies are 0/6.
  • RQ6 (execution, n = 6). Execution and validation are universally emulator-based and host-run (6/6; QEMU in 5/6); real hardware appears only in secondary roles — bug confirmation by re-execution (S20 P2IM) and an Avatar baseline (S21 HALucinator); HIL appears once, only as a baseline; five studies "explicitly avoid HIL and market hardware-independence as a design goal". No study executes its generated test suite primarily on physical hardware, no "Generation → Compilation → Real Hardware" flow exists, and the compilation of generated tests is reported nowhere.
  • RQ1 (test types, n = 4) supplies the complementary negative: no study separately qualifies its environment as real target hardware, simulator or emulator, and none reports a complete generation-to-pass funnel. The unit peak (S02, and S04 tran-mt25 — the only study emitting C test code) executes on host toolchains or reports no platform at all; the HIL peak executes on real industrial benches, but there the LLM-generated artefacts are system-level test steps, not C-level test code. S04's own record is the dataset's sharpest negative evidence on the core question: on Zephyr/RTOS code its generated tests were "often unusable without extensive manual modification", the authors "decided to stop further efforts", and concluded that LLMs are "not yet capable of fully autonomous test generation for large, framework-driven, or hardware-dependent software".

Interpretation, bounded. The conjunction "hardware specification in context × LLM interrupt/timing-test generation × HIL validation" (gap B10/U1) and "C-level test generation × hardware-relevant execution" (B14/U5) were never instantiated in any single verified study. This must be read as the conjunction of independent within-dataset zeros across non-overlapping datasets — the structure of the literature makes these combinations unobserved; it does not show them to be ineffective. Alternative explanations are retained per the gap analysis: hardware independence is an explicitly marketed design goal in cluster B, not a shortfall; delegation to mature infrastructure (S05's strongest configuration deliberately retrieves pre-existing doubles rather than synthesising them) may be an engineering conclusion rather than an omission; and RQ1's HIL peak shows LLM activity does occur on real benches, one abstraction level above C test code. What the evidence does support is the existence claim: no verified study has yet connected the two sides, and the missing middle layer — behaviourally faithful doubles with a quantified fidelity measure — is named by RQ4 as the most consistently reported yet least consistently measured dimension.

5.4 Interrupts, asynchronous behaviour and timing: modelling without LLMs, inherited time without control

Within RQ5 (n = 6; observations): asynchronous and timeout-related behaviour are reported by 6/6; interrupts are present in 5/6 targets, with ISR handling, interrupt injection, NVIC simulation, temporal assertions and delay handling at 4/6 each. Real-time property measurement (WCET, jitter, deadline validation, race-condition testing) is 1/6 for all four — concentrated in the single study S13 (Abtahi & Azim), whose own interrupt handling is "Not reported"; no study combines interrupt modelling with real-time property measurement. LLM involvement is limited to 2/6 (S17 path selection; S13 firmware/patch generation) and LLM-driven interrupt/async/timing test generation is 0/6; likewise nested interrupts and interrupt priorities were tested by 0/6 (RQ5-P1 explicitly excludes nested/tail interrupts; NVIC-capability mentions in S16 and S19 were removed by verification as inference). Time is inherited, never controlled: virtual/simulation time appears as a side effect of QEMU/Unicorn/Icicle/angr in 5/6, while fake/mock clocks, deterministic simulation-time mechanisms and clock-domain modelling are 0/6 — "temporal control in this literature is event-ordering control, not clock control" (Trend 4, verbatim). "Timeout" is universal as an engineering artefact (build budgets, path thresholds, failure modes) and absent as a tested property (0/6; Trend 5). OS-level RTOS semantics are 0/6 (scheduler modelling, task switching, thread interleaving, message/event queues), but this must be read together with the non-zero concurrency counts (Concurrency 2/6; explicit scheduling control 2/6, one of these being input-delivery scheduling, not OS scheduling; lock/mutex, semaphore and thread counts 1/6 each) — the accurate statement is OS-level scheduling semantics unmodelled, not concurrency unhandled. S13's virtualised environment was "configured" with interrupt latencies but these were not tested ("configured but not tested"), and the study itself states that virtualisation "cannot fully capture timing behavior, peripheral interactions, and resource constraints", deferring board-level validation (STM32/ESP32/Cortex-M) to future work; the only real-hardware interrupt testing (S16 IEmu, hardware as standard of truth) has no entry in the execution-environment dataset.

Convergence with the context side, causality barred. RQ5 records that all four interrupt-modelling studies obtain the interrupt model from the artefact under test, not from documentation (Trend 3), with S16 explicitly avoiding device-manual dependence; RQ3 independently records interrupt/timer/DMA specifications as LLM inputs at 0/8. The two populations do not overlap, so the tempting causal reading — "hardware documentation is missing from context, therefore models must be extracted from binaries" — is not testable in this evidence base. What is supported: in two independent datasets, hardware specification documents were exhaustively verified as absent — once from model input, once from model source. What is also supported as observation: extraction-from-artefact is a deliberate design choice in cluster B, an alternative explanation that weakens any deficit framing of the same zeros.

5.5 Feedback loops: closed everywhere, on the same signals

RQ7 (n = 5) reports loop closure as universal — automatic closed-loop refinement 5/5, with one-shot, manual, semi-automatic and mixed strategies at 0/5 — and quantified benefits where reported: iteration contributes roughly 40% of S24 CoverUp's successful test generations, and S26 LLMLOOP's loops raise pass@1 from 71.65% to 80.85% (pass@10 76.22% → 90.24%). The feedback sources that close the loops are execution results (5/5), LLM-generated corrections (5/5 — a mechanism label the source explicitly notes no paper terms "self-critique"), test failures (4/5), compiler errors (3/5) and coverage (3/5). Hardware-adjacent signals are thin: hardware/peripheral feedback 1/5 (S17's DMA input-channel emulation), runtime traces 2/5, sensor outputs 0/5, compilation warnings 0/5. The loop-saturated studies are mostly not embedded (embedded firmware in only 2/5; S24 Python, S25 Panta and S26 LLMLOOP Java), and the two embedded studies report no iteration budget (0/2; S13's stopping rule is qualitative).

Interpretation. The loops, as built, refine what tooling can observe: compilation, execution, coverage and static findings. The semantic dimensions that define hardware-aware embedded testing — registers, interrupts, timing, protocol behaviour — are exactly the signals the loop ingests least (1/5 hardware feedback, against context and dependency zeros above). This is again a convergence across datasets rather than a measured mediation: RQ7 shares only S13/S17 with the dependency/environment datasets, so we cannot claim that loop design causes the hardware gap — only that within the verified evidence, closed-loop machinery and hardware semantics are strongest where the other is weakest (compare S13: the only study with WCET/jitter/deadline feedback closing a patch loop, and simultaneously the study whose hardware validation is explicitly future work).

5.6 Metrics and validation: decoupled proxies and absent comparability

Within the RQ8 dataset (n = 4; observations): every study validates by execution (4/4) and benchmark comparison (4/4); compilation, mutation, simulation/emulation and coverage analysis appear in 2/4 each; real hardware, HIL, fault seeding, fault exposure, human evaluation, expert review and statement/branch/function/condition coverage are each 0/4; there is no common benchmark, no common baseline, no common quantified metric and no identical evaluation environment, and no study quantifies coverage and mutation score together. Where a metric name recurs (pass rate, execution success, fault detection), definitions and denominators differ across studies — the source bars pooling on exactly that ground. Two studies supply the dataset's decoupling evidence: MuTAP (S27) dropped coverage because "coverage is weakly correlated with fault detection" (even while reporting mutation score 93.57% ± 11.18 against Pynguin's 65.94%), and within RQ1, the AutoHIL ablation separates executability (89.15%) from functional correctness (50.51%) and accuracy (46.10%), while S02's generated tests reach an 84.5% runtime-validation rate yet sit below the human baseline on branch (43% vs 76%) and line (67% vs 93%) coverage. Because RQ1 × RQ8 overlap is zero, these are two disjoint datasets independently recording the same dissociation (observation + interpretation flagged as such).

Consequences (evidence-supported). (i) Quantitative synthesis is impossible: RQ1 states meta-analysis/effect-size synthesis "impossible" on its own evidence, RQ8 forbids prevalence claims at n = 4 — and this review's own execution of Section 4 follows that rule (no pooled rates anywhere). (ii) Quality claims about generated tests built on a single proxy — compilability, pass rate, or coverage — are unsupported by this dataset; the verified evidence actively contradicts the proxies' agreement. (iii) The metric that would matter most for hardware-aware C tests — fault detection against hardware-relevant behaviour (fault seeding/exposure) — has no verified instance. (iv) The funnel is never complete: no study reports generated → compilable → executed → passed on the same artefacts, and RQ6 adds that "compilation of generated tests is not reported in any paper" in its dataset; comparison across studies therefore compares different populations of artefacts.

5.7 Context reporting, reproducibility, and the reliability of this synthesis

Incomplete context reporting (type I observations). Model identity is unreported in at least one configuration for 5/7 RQ2 studies; prompting is unreported in at least one configuration for 5/7; specific peripheral types are entirely unreported in 3/6 RQ4 studies; 9/28 studies carry no recorded publication year; the corpus is preprint-heavy (6/7 of RQ2 are arXiv preprints with only one peer-reviewed venue; DOIs are largely absent across RQ1/RQ2/RQ7; one included study is a master's thesis admitted under the grey-literature decision). Interpretation, stated plainly: these are limits on auditability of this review's own conclusions — for instance, no future cross-study test of "which strategy yields which validation outcome" can even be assembled retrospectively because 5/7 studies leave the strategy field partially blank. They are not evidence that the wider literature fails to report such information.

Reproducibility. The only reproducibility-related limitation verified at the study level in RQ9 is closed-source model dependency (1/6 — S13's GPT-4 reliance); per the single-study rule this is recorded as a single-study gap, not a literature-wide one. Reporting absences for prompts, datasets, source code or hardware settings were not verified as limitations (0/6, type II) and are therefore not converted into a reproducibility-gap claim.

Counter-intuitive silences (must be stated with their limits). The RQ9 verification layer found hallucination, incorrect/invented APIs, named reasoning-limitation categories, formal threats-to-validity sections, statistical analyses, HIL, HAL and RTOS-as-limitation discussed by 0/6 studies (type II: silence, not absence). Meanwhile the LLM-side weaknesses that were author-acknowledged are concrete and different: missing context causing ~60% and model logical inconsistency causing ~40% of S13's compilation failures; LLM-as-a-judge verdicts "unreliable and inconsistent across runs"; independently generated solutions "converging to functionally correct designs with similar security weaknesses"; the LLM functioning "as a heuristic guide" whose bad suggestions do not block exploration (S17). One observation from the other side of the corpus complicates the silence: S10 (Englhardt et al., RQ2 dataset, not among the six RQ9 studies) records a register-level fabrication failure — GPT-3.5 compiled code that hallucinated at least one register address or configuration value in 100% of programs, and GPT-4 produced verifiable working IMU code in 16% of cases (14% and 66% variants of the same study's figures are recorded in different sections; §4.11 N4-type multi-version caution applies to every number quoted from this study). The honest composite: fabrication-type failures are observed in extracted data where the study looked for them, but were never verified as an acknowledged limitation within the RQ9 population; research programmes targeting "hallucination reduction" as the field's bottleneck therefore lack support in this dataset's verified failure profile, while the dataset's actual verified failure modes (context loss, inconsistency, judge instability) point elsewhere.

Reliability of the synthesis itself. The RQ9 evidence was downgraded in verification for 23 of 75 retained instances (30.7%) and 4 instances rejected; instance counts were never substituted for study counts (S17 alone contributes 13/75 = 17.3% of instances but one study per category). RQ8's summary contains nine internal count conflicts on non-zero magnitudes — its zero rows used above are unaffected — and several source papers carry unreconciled internal numbers (§4.11 N4, N5). Eight identity/terminology matters remain pending author adjudication (V1–V8), of which M2 (S13's identity as R4_p4) is structural: it decides whether the clusters are connected at all. Interpretation: these are limitations of this review's evidence base, not findings about the literature; Section 7 (Threats to Validity) is the proper venue for their procedural treatment.

5.8 Synthesis: what the combined evidence does and does not establish about hardware-aware embedded C test generation

Across the nine RQs, one composite picture survives the overlap constraints (each element observation-anchored; the composite reading flagged as interpretation):

  1. The generation side is real but software-anchored. LLMs generate unit-level tests, stubs and hardware-adjacent production code (19/27 RQ4 configurations), with retrieval and agentic repair loops demonstrably raising compile/execution success in general-purpose settings (S05 96.1% compile-and-link; S09 95.7%/86.5% retrieval+agentic vs 69.5%/56.4% direct; the loop gains in 5.5). What the loops and retrievals act on is code, build and coverage signals — not hardware semantics (5.2, 5.5).
  2. The hardware side is handled by non-LLM infrastructure. Dependencies are delegated (5/6), interrupts are modelled from binaries (4/4 modelling studies), time is inherited from emulators (5/6), execution is emulator-bound (6/6) and physical hardware appears only to confirm or baseline (2/6, secondary). Where LLMs touch real-time properties (S13), validation is virtualised by the study's own admission, and its interrupt latencies were configured but not tested.
  3. The connective tissue is missing, and the studies say so. Behaviourally faithful doubles: 0/27; fidelity measurement: 0; LLM-generated tests executed on hardware-relevant substrates: 0; LLM generation of interrupt/timing tests: 0/6; oracle techniques beyond pass/fail and hardware-behaviour references: absent with one verified empirical leak (S20-lineage's PLC bug that the simple memory-error detector missed, recorded in RQ9-P6 L8). The field's own future-work statements cluster on exactly these connections — extending validation to physical boards (S13), peripheral abstraction beyond DMA (S17), input-duration-aware fuzzing (P2IM lineage), more powerful LLMs (S13 and S17, the only future direction proposed by two studies) — while metamorphic testing as an oracle alternative comes from the generic survey (RQ9-P4).
  4. Evaluation cannot yet arbitrate between these positions (5.6): incomparable metrics, incomplete funnels and decoupled proxies mean the current evidence can describe where effort is spent but not what it buys in test validity.
  5. The construct itself has no complete referent yet (5.1): "hardware-aware LLM-based embedded C test generation" names a conjunction that no verified study realises end-to-end; the four elements exist in separate literatures whose bridge (M2) is still unconfirmed.

5.9 Practical implications (grounded in the verified evidence)

  • Do not deploy for autonomous hardware-in-the-loop test authoring; deploy where the evidence sits. The verified positives are host-level unit-test generation with LLM-generated stubs on software-artefact context (S05 — the single unambiguous case), retrieval grounding over repository artefacts, and closed-loop repair against compiler/test/coverage signals (S24, S25, S26). Expect LLM output on framework-driven, macro-heavy, hardware-dependent C (Zephyr-class) to require substantial manual work — this is a direct, single-study negative result (S04), stated at its evidential weight.
  • Treat timing verdicts from emulator-grade environments as provisional. The verified pattern is event-ordering without clock control (0/6 fake/mock clocks, 0/6 deterministic time mechanisms), timeouts as budgets rather than tested properties, and one study's own admission that virtualisation cannot capture timing/peripheral/resource behaviour. Real-time claims about embedded C tests need physical confirmation in the P2IM sense (re-execution to confirm) or the HALucinator sense (baseline comparison) — both currently one-off practices, or the RQ1 HIL-bench sense — with the funnel actually reported.
  • Judge generated tests by multi-proxy evidence, never by one number. Executability, coverage and fault detection dissociate within two independent datasets (5.6). Practically: report compilable/executed/passed as separate stages against a fixed denominator, and when validating embedded tests, include fault-relevant checks (seeded or scenario-level) rather than pass/fail alone.
  • Keep human gatekeeping where the datasets place it. In the industrial HIL/generation studies, humans accepted 38.9%, modified 55.6%, rewrote 5.6% of EmbC-Test artefacts (multi-version caution: the triple sums to 100.1% in the source), 25.79% of scripts needed manual edits, and equivalence and defect validity rested on expert review. RQ7's opposite signal (human involvement 1/5, "shrinking to a gatekeeping role") comes from a mostly non-embedded population; the divergence is unresolved (§4.11 N5-adjacent, D-6) and should be read as domain composition, not as a trend to plan against.
  • Make selection of dependency strategy an explicit engineering decision. The two verified families — synthesise doubles host-side vs delegate to existing platforms — have never been combined in one study; teams needing both isolation and hardware realism must currently integrate across the boundary themselves, because no verified recipe exists.
  • Require reporting that would let you re-use the work. Given model-identity and prompting gaps (5/7 each), practitioners adopting published pipelines should expect to re-derive prompts, toolchain pins and board configurations rather than replay them.

5.10 Research implications (directions traceable to the evidence, with status labels)

Author-side, before new data collection (derived; lowest cost). Adjudicate the eight pending items V1–V8; V1 (M2) in particular determines whether any cross-cluster statement in this review survives in its current strength. Until resolved, published text should not describe RQ4 and RQ5–RQ7 findings as evidence about the same study population.

The highest-leverage single study (derived from C1/C2). Produce and report one study that instantiates all four elements simultaneously — LLM generation of embedded-C tests, hardware-specification-informed context, execution on a hardware-relevant substrate (emulator with modelled peripherals, HIL, or board), and a complete funnel — reusing verified artefacts to create the first same-study pairing (e.g., S17's ten firmware samples, P2IM's device set, S04's C-level test material, S05's stub pipeline). Under the current overlap structure, only such studies can convert cross-dataset contrasts into paired evidence.

Context and grounding (author-stated need: peripheral abstraction beyond DMA, S17; derived elsewhere). Test whether register maps / peripheral specifications supplied at inference time — retrieved or structured — change generated-test behaviour on register-access and interrupt paths, against two verified baselines: the software-artefact-only RAG pattern (0/8 hardware-document retrieval) and the extraction-from-artefact pattern (4/4 studies; S16's deliberate manual-avoidance). The alternative explanation that artefact extraction is superior must be preserved as a live hypothesis, not dismissed.

Interrupts and timing (author-stated: input duration as "an open challenge for future research", P2IM-lineage; derived: LLM-side). Build LLM-facing representations on top of the interrupt models the cluster-B artefacts already extract (IRQ models, Interrupt Model Tables, rule extraction), targeting the verified zeros: nested interrupts, priorities, ISR-sequence tests, timeout-as-tested-property. Two preconditions from the data: first unify terminology (timeout referents differ 6/6; simulator/emulator classification D-2 pending), and introduce controllable virtual clocks so duration/periodicity become observable quantities; note the scope caveat that some 0/6 counts (e.g., RQ5-P1's nested-interrupt exclusion) bound current studies' claims, not the construct's feasibility.

Doubles, fidelity and oracles (mixed provenance). Construct behaviourally faithful doubles (register/timing/interrupt/protocol semantics) and — critically — a fidelity measure, since the dataset shows the dimension "most consistently reported, least consistently measured" (RQ4). In parallel, develop hardware-behaviour test oracles: the verified leak (S20-lineage PLC bug missed by a memory-error detector) and the acknowledged oracle problem (3/6, strongest at RQ9-P4/P5/P6) define the case; metamorphic testing is author-proposed but has no in-dataset evaluation, and LLM-as-a-judge is a verified unreliable option — neither should be adopted on this evidence alone.

Evaluation infrastructure (author-stated at two studies: specialised/diversified benchmarks, RQ9-P4; security-specific evaluation, RQ9-P5). A shared embedded-C test-generation benchmark must fix MCU family, compiler/toolchain versions, dependency infrastructure, and the four-stage funnel definition, on code unseen during pretraining (leakage: verified concern, RQ9-P4 L4); it should pair coverage with mutation/fault-seeding in one instrument, because the verified dissociation claims (5.6) are otherwise unresolvable. Cost is real: the one large-scale benchmark effort in the RQ9-derived evidence set (HardSecBench lineage, RQ9-P5 — outside the 28-study corpus) documents expensive construction — but it also demonstrates feasibility.

Layered dependency handling (derived, flagged as structurally weakest). Combine LLM doubles at unit level with emulator/HIL execution at integration level — the strategy RQ4 records as never instantiated — and report it inside one study to break the zero-overwall between the replacement and provision families.

**What this evidence does not support as a research priority (derived prohibitions, kept for balance):** framing the bottleneck as hallucination or API invention (0/6 verified as limitation in RQ9; the verified failure modes are context loss, inconsistency, judge instability, convergent weaknesses — the type-II rule means this is "not supported here", not "not a problem"); claiming the literature "ignores" HIL, HAL or RTOS (all type-II silences); and pursuing model-capacity work justified by prevalence statistics this corpus cannot lawfully produce (denominator bounds, §4.11 N1).

5.11 Scope of the interpretive claims in this Discussion

Every statement above is bounded three ways, and these bounds should travel with any citation of this review. First, dataset-relativity: each count describes its own verified sample (sizes 4–8 for RQ1–RQ8; 6 studies at study level for RQ9), and all percentage-extrapolation bans quoted in §4 remain in force. Second, classification-dependence: the zeros inherit our taxonomic lens, and the data record that the lens moves counts — the same QEMU/Unicorn tools sit on opposite sides of a simulator/emulator boundary in two datasets (D-2, pending), "mock" names both a unit double and a system-level simulation verb, "feedback" covers both evaluation-only measurement and refinement input, and "coverage" in one study denotes fault-scenario coverage. Third, search-scope dependence: a different terminological net (re-hosting, cyber-physical test generation, model-in-the-loop, digital-twin testing and similar vocabulary — none of which structured the present extraction) could populate cells currently at zero; accordingly this Discussion asserts that the combinations named in 5.3–5.10 are unobserved within the verified corpus, and no stronger claim anywhere in this section should be quoted.

6. Research Gaps and Future Directions

6.0 How this section reads the evidence

Five rules from Section 4 govern every claim below, and they are what keep a gap section from becoming a wish list.

  1. Direction of derivation. Each theme here was named only after inspecting the verified matrix; none was assumed first and matched to evidence afterwards.
  2. Type I versus type II zeros. A zero at the level of method use ("did any verified study do X?" — no) supports an underexplored-within-this-dataset claim. A zero at the level of limitation discussion ("did any study call Y a limitation?" — no) is silence, not absence, and licenses no gap claim. Both appear below and are never interchanged.
  3. Evidence grades. EA = author-acknowledged limitation, confirmed by the RQ9 verification files; EA-q = acknowledged but downgraded in verification; SI = synthesis-inferred from adjacent evidence; IFS = inferred from silence; NE = not established (type II); NR = not in the study's scope. Study counts, never limitation-instance counts (the 75 retained instances, 30.7% of which were downgraded in verification), carry the prevalence reading.
  4. The composite ceiling. No study in the verified dataset is simultaneously LLM-based, test-generating, embedded-C-source-level and hardware-aware [RQ9 §0.5], and 14 of the 28 pairwise overlaps among the RQ1–RQ8 study sets are zero (§4.9.4). Every cross-dimensional gap below is therefore a conjunction of independently verified zeros across disjoint datasets — it shows that a combination is unobserved, never that the combination fails.
  5. Provenance of directions. Each proposed direction is labelled author-stated (verbatim future work from a verified study) or review-derived (our inference from the evidence, with its preconditions and a stated reason it might not pay off). Single-study items (1/6 in RQ9, or 1/4, 1/7 etc. elsewhere) are marked as such and are not inflated into field-level gaps.

The gap analysis supports all seven candidate themes, but not equally: themes 6.1–6.4 rest primarily on author-acknowledged limitations plus exhaustive type-I zeros; 6.5 is a composition gap rather than a method gap (closed-loop feedback is saturated as a technique); 6.6 rests on two disjoint datasets independently negating comparability plus two author-stated benchmark gaps; and 6.7 (reproducibility) is the weakest, where most of the expected evidence is type-II silence and must not be claimed.

6.1 Peripheral-aware test generation

Observed evidence. Peripheral dependence is the most consistently verified hardware gap in the RQ9 matrix: 4/6 studies acknowledge it (EA), each in its own words — ADFEmu (S17) abstracts DMA only and admits that identifying how any peripheral "can be abstracted for dynamic analysis purposes, in a hardware-independent and firmware-compatible way" is "an interesting research topic that we would like to pursue in the future" [L11]; Abtahi & Azim (S13) generates networking-protocol code (MQTT) "with only minimal detection and parsing" [L9]; HardSecBench (RQ9-P5) finds open-source models show "limited gains on categories involving peripherals and interface/I-O" [L11, qualified]; and the P2IM-lineage study (RQ9-P6) describes peripheral heterogeneity, differing access conventions and incompatible fuzzer input interfaces as challenges "unique to MCU firmware fuzzing" [L2, narrowed]. On the type-I side: no specific peripheral class — SPI, Ethernet, DMA, interrupt controllers, Flash/EEPROM, device drivers, HAL APIs — was assessed as a dependency in any of the six RQ4 studies (each 0/6, though specific peripheral types are simply unreported in 3/6, S05/S13/S14); a formal peripheral specification reached model context in only 1/8 RQ3 studies (S06, EmbedAgent); and among the studies whose LLM role is genuinely test generation, confirmed hardware context is 0/3 (S02, S05, S12) (§4.3). The correct matrix reading matters: 4/6 does not mean "four of six have a peripheral problem and two do not" — it means four acknowledge it, one (Asmita et al.) explicitly reports no hardware-aware limitations at all, and one (RQ9-P4, the generic survey) is out of scope.

Scarcity versus reporting absence. The core of this theme is genuine method scarcity: dependency handling was assessed as absent-by-design in five of six RQ4 studies (delegated outward), and LLM-built peripheral models or device drivers number zero. The peripheral-type breakdown, by contrast, is partly reporting absence — 3/6 studies leave specific types unrecorded, which undercounts rather than overcounts the true handling landscape.

Why it matters, bounded. Peripheral interaction is what distinguishes embedded-C testing from general-purpose test generation; without any abstraction layer beyond the one DMA channel S17 models, generated tests cannot reach device behaviour at all, and the validation claims in Sections 4.4–4.6 remain claims about software-executing-on-software. This statement rests on within-dataset exhaustions (RQ3, RQ4) plus RQ9's EA tier; it does not depend on any cross-dataset pairing.

Directions. (a) Author-stated: peripheral abstraction beyond DMA — counters, comparators and similar classes — which S17 names as future work while noting it offers "no roadmap" [L11]. (b) Review-derived: extend S06's verified context stack (the only confirmed peripheral specification, plus board, pinout and schematic, with 13 pre-registered configurations) from hardware-adjacent production-code generation toward test generation with explicit peripheral semantics, reusing its own Wokwi-based rig — the lowest-risk starting point in the corpus because the context pipeline already exists. Precondition: the fidelity measure of 6.2, or the new tests repeat the verified pattern of "handled but never validated as faithful" (quantitative fidelity assessment: 0/27 configurations).

6.2 Register and datasheet grounding of model context

Observed evidence. Eleven categories of hardware specification — register map, MCU/processor specification, board documentation, clock configuration, memory map, electrical/interface, sensor/actuator, communication-protocol, interrupt, timer and DMA specifications — are each 0/8 as confirmed LLM inputs (RQ3), and the three retrieval combinations (datasheet+RAG, register map+HAL, HAL+driver+peripheral specification) are all zero: whatever the five RAG-using studies retrieved, it was exclusively software artefacts (legacy tests, repository structure, build logs, dependency lists, known-good #include directives). The two studies that did expose datasheets are instructive exceptions that prove the rule: S08 (H2LooP) puts them into the model through training-time weight consolidation over a 117-vendor corpus, not inference-time context, and does not generate tests; S11 (SpecMap) uses datasheets for specification traceability rather than test authoring. On the acknowledgment side, registers are an author-stated limitation in exactly one study (P2IM-lineage [L3], "a limitation of our register categorization method"); ADFEmu's RAM-stored DMA-descriptor gap and Abtahi & Azim's MMIO abstraction are SI adjacent items, not author statements (§4.9 composition notes; V6 pending for the adjacent gap row G5).

Scarcity versus reporting absence. RQ3 itself draws the line: three of eight studies carry no hardware-context record at all despite working on hardware-dependent code, so the honest wording is "no evidence that context was provided", not "confirmed not provided". The 0/8 figures are therefore exhaustive over what the dataset can show — strong as type-I under-exploration, weak as claims about what models could do.

Why it matters, bounded. Registers are the substrate on which peripherals, interrupts and timing are actually expressed in C; their absence from context means the generation machinery operates one level above the hardware semantics the review's title asks about. The direction of convergence noted in §5.2–5.4 — hardware documents absent from context (RQ3) and, in a disjoint population, interrupt models deliberately extracted from binaries rather than manuals (RQ5 Trend 3, 4/4) — is a structural contrast, and we do not upgrade it to a causal story.

Directions. (a) Review-derived, with live counter-hypothesis: run the comparison the dataset never instantiates — datasheet/register-map material supplied as inference-time retrievable context versus the artefact-extraction route versus training-time consolidation, on the same target board and same test suite. The counter-hypothesis must be preserved, not waved away: extraction-from-artefact is an explicit design choice in cluster B (S16 "explicitly avoiding device-manual dependence"), and if manuals are unavailable, version-mismatched or unparseable, grounding may not pay — which is exactly what no verified study has measured. (b) Precondition (review-derived): define a quantitative virtual-to-physical fidelity measure first; RQ4 records that no fidelity measure appears anywhere in the dataset and that this dimension is "most consistently reported … and the least consistently measured" — without a metric, "faithful grounding" is unfalsifiable. Terminology caution retained: the RAG-coding conflict between RQ2 (5/7) and RQ3 (3/8) is unresolved (V4), so stability of the "datasheet+RAG = 0" cell depends on that adjudication.

6.3 Interrupt, asynchronous and timing behaviour

Observed evidence. Within RQ5 (n = 6), the modelling machinery exists without the generator: interrupts are present in 5/6 targets; ISR handling, interrupt injection, NVIC simulation and temporal assertions at 4/6 each — but LLM-driven interrupt/async/timing test generation is 0/6, nested interrupts and interrupt priorities were tested by 0/6 (the priority mentions in S16/S19 were struck by verification as inference, making this a strict zero), and time itself is inherited from emulators (5/6 virtual-time-as-side-effect) while fake/mock clocks, deterministic simulation-time mechanisms and clock-domain models are each 0/6. "Timeout" is reported 6/6 with six different referents and validated as a firmware property 0/6 (Trend 5). Real-time property measurement is 1/6 for WCET, jitter, deadline validation and race-condition testing alike, concentrated in S13 — whose own interrupt latencies are "configured but not tested" [EA, L10] and which concedes virtualisation "cannot fully capture timing behavior" [L1]. S13's semantics gap is acknowledged at study level (G4/G5 at 3/6 each, EA tier — with the G5 attribution warning V6), and the only real-hardware interrupt testing in the corpus (S16, hardware as standard of truth) sits outside the environment dataset entirely.

Scarcity versus reporting absence. Three sub-cases must be read differently: (i) genuine method scarcity (no LLM has been pointed at interrupt-test generation in any verified study); (ii) scope-setting, not incapability (RQ5-P1/S15 explicitly excludes nested and tail interrupts — a boundary of that study, not evidence against the construct; the verification files even bar reading P2IM's out-of-scope items as future work, "'Out of scope' does not automatically equal future work"); and (iii) terminology artefact — the timeout numbers are hostage to six incompatible definitions, so the zero partly reflects our classification lens. Against over-cleansing: the concurrency/scheduling zeros are not absences of concurrency handling — RQ5 records Concurrency 2/6, explicit scheduling control 2/6 (one of them input-delivery scheduling, not OS scheduling), and semaphore/lock/race/mutex at 1/6 each; the accurate claim is OS-level scheduling semantics unmodelled, and the RTOS/concurrency literature-silence (0/6 discussed as limitation) remains type II and is not claimed as a gap.

Why it matters, bounded. Interrupts and timing are the named constructs of this review's subtitle. The verified picture is that the community can represent interrupt models (four ways, from binaries) but has never asked an LLM to test them, and can measure real-time behaviour in exactly one virtualised study that says the virtualisation is insufficient. If the field's ambition is hardware-aware test authoring, this is where the machinery and the generator currently fail to meet.

Directions. (a) Author-stated, strongest in the dataset: input-duration-aware testing — the P2IM-lineage study calls the fact that "neither P2IM nor existing fuzzers consider input duration" "an open challenge for future research" [L6, fully supported], which converts one of the trend-4/5 zeros into a named target. (b) Review-derived: use the interrupt artefacts cluster B already produces (S15's symbolic-execution IRQ model, S16's binary-extracted interrupt-triggering rules, S19's Interrupt Model Table) as structured inputs to an LLM test generator, targeting ISR sequences, then the verified zeros of nesting and priorities; start on the four studies that already have NVIC simulation. Precondition: unify the timeout and time-control vocabulary before new counts are published, or the next synthesis inherits the same six-way referent split. (c) Review-derived: controllable virtual clocks (fake/mock clock, deterministic simulation time) as mechanisms, so delay-duration and periodic execution become tested properties rather than emulator by-products — with the honest caveat from Trend 4: if a firmware's correctness depends only on event ordering, clock control's marginal value is limited, which is precisely an open empirical question no verified study answers.

6.4 Realistic execution validation (hardware-in-the-loop and physical targets)

Observed evidence. This theme carries the highest study-count in the RQ9 matrix, with a double count that must travel together: 5/6 studies acknowledge that execution validation is present but never hardware-grounded (EA tier), while only 2/6 (S17, S13) lack real-device evaluation as a verified gap — the P2IM-lineage study explicitly did re-execute crash- and hang-inducing inputs on physical MCUs to confirm bugs, and our verification files bar listing "lack of real hardware evaluation" against it. The type-I evidence converges from three disjoint directions: LLM-generated tests combined with a simulator, emulator, HIL rig or real hardware number zero studies in RQ4; real hardware is a primary execution environment in 0/6 RQ6 studies, appearing at all in only 2/6 and then only for confirmation or baseline, with five studies "explicitly avoid[ing] HIL and market[ing] hardware-independence as a design goal"; and 0/4 RQ8 studies validate with real hardware or HIL (§4.4, §4.6, §4.8). The one reverse datapoint in the corpus sharpens rather than softens the gap: the two RQ1 HIL studies execute LLM-generated artefacts on genuine industrial benches at 100% execution rate (dSPACE SCALEXIO, RTICANMM, real ECUs) — but the generated objects there are system-level test steps, not C-level test code, and S04, the only study emitting C test code, abandoned Zephyr-level attempts as "often unusable without extensive manual modification".

Scarcity versus reporting absence. The scarcity is real (type I, exhaustively verified across RQ4/RQ6/RQ8), but two framings must be quarantined. First, HIL-as-limitation is a type-II zero (0/6; "the single cleanest void… 'Not reported' in all six files") and cannot be converted into "the literature ignores HIL" — especially given RQ1's live HIL usage. Second, hardware-independence is marketed as a design goal in cluster B; the missing HIL papers may partly reflect deliberate positioning (and venue economics), not collective oversight. A third, narrower absence is reporting-level: RQ6 records that compilation of generated tests is reported nowhere in its dataset — a pure reporting gap sitting underneath the validation gap.

Why it matters, bounded. Everything the review calls "hardware-aware" ultimately needs a hardware-behavioural verdict: today's verified verdicts come from emulators whose fidelity nobody measured (6.2) and whose time is inherited (6.3). The gap matters because it leaves the review's own construct without its final element — not because we may assert that emulator-only validation is wrong, but because no verified study has yet shown what changes when the same tests run closer to the metal.

Directions. (a) Author-stated: physical-platform validation on STM32, ESP32 and ARM Cortex-M boards — Abtahi & Azim's named plan [L12] — and P2IM-style real-device bug confirmation as an existing, replicated template (S20) for how to close at least part of the loop. (b) Review-derived, and the section's top structural priority: produce the first study that instantiates all four construct elements at once — LLM generation of embedded-C tests, hardware-informed context, execution on a hardware-relevant substrate (peripheral-modelled emulator, HIL, or board), and a complete generated → compilable → executed → passed funnel. Under the current overlap structure (14 of 28 pairs at zero), only such a study can create within-study pairing; single-dimension additions cannot. Reusing verified artefacts — S17's ten firmware samples, S20's device set, S04's C-level test material, S05's stub pipeline — is the lowest-variance route, and the negative evidence from S04 should size expectations (assisted, human-gated authoring, not autonomy).

6.5 Closed-loop feedback: a composition gap, not a method gap

Observed evidence and retention judgement. Checked against the dataset, "closed-loop feedback" fails the criteria for a classical gap and is retained in a narrower form: automatic closed-loop refinement is saturated (5/5 in RQ7; one-shot, manual, semi-automatic and mixed strategies each 0/5), and where iteration was quantified it helped — ~40% of S24's successful generations come from refinement; S26's loops lift pass@1 from 71.65% to 80.85%. The verified shortfalls are three, and each is distinct: (i) composition — only 2/5 feedback studies target embedded firmware at all (S24 is Python; S25/S26 Java), so the saturation statement mostly describes general-purpose test generation; (ii) signal breadth — the loops close on execution results (5/5), LLM corrections (5/5), test failures (4/5), compiler errors (3/5) and coverage (3/5), while hardware/peripheral feedback is 1/5 (S17's DMA channel emulation), runtime traces 2/5, sensor outputs 0/5 and compilation warnings 0/5; and (iii) downstream reporting — the two embedded studies report no iteration budget (0/2), one of them stopping on a qualitative criterion ("until a stable, secure, and real-time-compliant firmware iteration is achieved"). The oracle problem sits directly under this theme in the RQ9 matrix: 3/6 acknowledge it (EA; strongest at RQ9-P4's "persistent test-oracle problem"), and it is the only gap in the RQ9-derived evidence set with a demonstrated leak — a real PLC bug that fired under test "went undetected by the simple memory-error detector" (P2IM-lineage [L8]). All three of its supporting studies (RQ9-P4, RQ9-P5, RQ9-P6) lie outside the 28-study corpus.

Scarcity versus reporting absence. Missing hardware-adjacent feedback is method scarcity; missing loop budgets is reporting absence (the loops ran; their stop conditions were not written down); and the effectiveness of loops on embedded targets specifically is neither — it is simply untested, since loop frequency is not loop validity and the quantified gains come from the non-embedded majority of the dataset.

Directions. (a) Author-stated: additional coverage instrumentation as explicit future work (S13 [L8]); metamorphic and other additional test oracles as the survey's named remedy (RQ9-P4 [L2], coded "one of the strongest RQ9 findings"). (b) Review-derived: extend verified loop architectures to hardware-adjacent signals the emulators already emit — MMIO/NVIC/register-state traces, DMA events, WCET/jitter/deadline measurements — treating oracles at three explicit layers (syntactic, functional, hardware-behavioural) rather than pass/fail. Two evidence-based cautions: LLM-as-a-judge is a verified-unreliable oracle candidate ("inconsistent across runs", RQ9-P5 [L7, Part]), and metamorphic testing, though author-proposed, has no in-dataset evaluation — the first study adopting it should be designed to produce that evaluation, not assume it.

6.6 Standardised benchmarks and metrics

Observed evidence. Two disjoint datasets independently negate comparability. RQ8 (n = 4): no common benchmark, no common baseline, no common quantified metric, no identical evaluation environment (each 0/4); fault seeding, fault exposure, human evaluation and expert review each 0/4; no study quantifies coverage and mutation score together; and where a metric name recurs across studies, definitions and units differ, which the source treats as barring any pooling. RQ1 (n = 4): four mutually incompatible execution-accounting regimes, no complete funnel anywhere, and its verdict that quantitative meta-analysis "is impossible". The proxy-decoupling evidence — the AutoHIL ablation separating executability (89.15%) from functional correctness (50.51%) and accuracy (46.10%); S02's 84.5% runtime validation against branch/line coverage (43%/67%) below the human baseline (76%/93%); MuTAP dropping coverage for "weakly correlated with fault detection" — comes from these same two populations and is reported with the multi-version caveat where the source figures conflict (§4.11). Author acknowledgment exists at study level too: no widely recognised benchmark for unit-test generation and pretraining leakage inflating results (RQ9-P4 [L3, L4]); lack of a standardised, comprehensive benchmark and the need for security-specific evaluation (HardSecBench [L2, L16]).

Scarcity versus reporting absence. All three coexist and must be told apart: method scarcity (nobody has built a shared embedded-C test-generation benchmark in the corpus); reporting absence (funnel stages and denominator definitions left unstated across datasets); and internal inconsistency — RQ8's own summary carries nine count conflicts on non-zero magnitudes (its zero rows, which this section relies on, are unaffected) — which is a property of this review's extraction, not of the literature. One overclaim guard applies: "benchmarks are missing" is scoped to embedded-C test generation; HardSecBench itself (924 validated tasks, 4,425 test cases) proves that large benchmark construction is feasible and expensive in this adjacency.

Why it matters, bounded. Metrics are the arbitration layer for 6.1–6.5: until execution success, coverage and fault detection are defined and reported compatibly, the field cannot say which of the missing combinations above would actually help, and this review could not lawfully compute any pooled rate.

Directions. (a) Review-derived, consolidating four author-stated asks: a shared benchmark for embedded-C test generation that pins target MCU family, compiler/toolchain versions, dependency infrastructure, and a complete four-stage funnel definition, uses code unseen during pretraining [RQ9-P4 L4], and instruments coverage together with mutation/fault seeding so the decoupling claims become testable rather than anecdotal. (b) Author-stated: security-specific evaluation as a mandatory layer alongside functional refinement loops [RQ9-P5 L16], motivated by the corpus's verified finding that functional refinement yields little security gain and independent generations converge on similar weaknesses.

6.7 Reproducibility (retained, with the weakest evidential footing)

Observed evidence and retention judgement. This theme is retained only in a disciplined form. The only reproducibility-related limitation verified at study level in RQ9 is closed-source model dependency (1/6; S13's GPT-4 reliance [A14]) — under the single-study rule, an observation, not a field-level gap. The expected evidence for broader reproducibility claims is type-II silence: "missing prompts/datasets/source code/hardware settings/benchmark details" are each discussed as limitations by 0/6 files, and P2IM-lineage's "manual architecture-specific model" item was removed in verification because the paper states the design extends to AVR, MIPS and RISC-V — so this section does not claim the literature fails to report its artefacts. What can be stated are type-I reporting-completeness facts about our own corpus: LLM identity and prompting are each unreported in ≥1 configuration for 5/7 RQ2 studies; 6/7 are arXiv preprints with one peer-reviewed venue; DOIs are absent across most datasets; year is unrecorded for 9/28 studies; and for 18 of the 28 studies the full-text evidence in our files is per-record verification documents rather than publisher PDFs (§4.11 N3).

Why it matters, bounded. These completeness gaps limit what anyone can later verify: retrospective cross-study tests of "which strategy, which validation outcome" cannot even be assembled when the strategy field is partly blank, and independent re-runs of the reviewed pipelines are frequently impossible as published. That is a statement about auditability, not about authors' lab hygiene.

Directions. (a) Review-derived, folded into 6.6: the shared benchmark should require artefact disclosure as an entry condition — model and version pinned per configuration, prompts or their hashes, toolchain versions, and the execution substrate — turning completeness into a publication incentive rather than an exhortation. (b) Author-side, requiring no new literature: adjudicate the eight pending verification items V1–V8 before extending the corpus [review-derived from C3/C5/C6]. V1 (whether R4_p4 and Abtahi & Azim are one study) decides whether the two research clusters are connected at all; its failure would downgrade every cross-cluster statement in Sections 5–6 by one strength level, which is why this zero-cost step is placed ahead of most new data collection.

6.8 Limitations of this review's own search scope, attached to the gaps above

Each gap above inherits the same boundary conditions, and they should travel with any citation of this section:

  • Every zero is lens-bound. Each 0-count means "not observed within the verified dataset under our classification scheme", never "no such study exists". The dataset itself shows the lens moves counts: the same QEMU/Unicorn tooling is coded "simulator 6/6" in one extraction and "simulator 0/6" in another (D-2, pending V3); "mock" names both a unit double (S05) and a system-level simulation verb (S14); "coverage" denotes fault-scenario coverage in one RQ1 study; and "feedback" covers both evaluation-only measurement and refinement input (the reason S13's coverage use is coded Not reported, not Yes, in RQ7).
  • Terminology reach. The extraction organised studies around the review's RQ vocabulary. Adjacent literatures the records do not show as covered — re-hosting as a named term, cyber-physical or model-in-the-loop test generation, digital-twin testing — could populate cells currently at zero; no claim of exhaustive coverage of those vocabularies is made, and none of the gap statements above should be read as one.
  • Small denominators. RQ study sets run 4–8; RQ9's study denominator is 6 with instance counts (75 retained, 30.7% downgraded) never substituting for studies; a single study moves RQ1 percentages by 25 points and RQ2 percentages by 14.3. All prevalence language in this section is bounded to its own denominator, and no cross-dataset rate is computed anywhere.
  • Unresolved conflicts, unadjudicated. The nine RQ8 internal count conflicts, the RAG-coding difference (V4), the simulator terminology split (V3), the interrupt-gap attribution (V6), the HIL-label sensitivity in RQ4 (D-9: one study's classification moves HIL popularity 33.3%→16.7%), and the preserved multi-version source figures (D-8) are reported as conflicts, not resolved; directions keyed to them (6.2, 6.3, 6.7) carry that conditionality explicitly.
  • No causal claims. Because 14 of 28 study-set pairs share zero studies, statements linking dimensions across RQs remain structural contrasts throughout Sections 5–6; the gap inventory says what has never been jointly observed, not what would fail if jointly attempted.

6.9 Closing orientation

Ranking below is our editorial judgement (review-derived), ordered by what each repair adds to the structure of the evidence rather than by the size of any single deficiency: (1) the four-element instantiation study of 6.4, the only design that creates within-study pairing; (2) the zero-cost V1–V8 adjudication of 6.7; (3) the benchmark-and-funnel instrument of 6.6, which turns proxy decoupling into a testable question; (4) the fidelity measure and layered oracles of 6.1–6.2 and 6.5, without which faithfulness and validity claims in this domain cannot be stated at all; then the domain-specific build-outs — hardware-spec grounding trials (6.2), interrupt-aware generation on existing models and controllable clocks (6.3), hardware-adjacent loop signals (6.5), and beyond-DMA peripheral abstraction (6.1). Each item is traceable, in the subsections above, to a specific verified count, a named study and an evidence grade; none is offered as established necessity.

7. Threats to Validity

This section assesses the threats to the validity of this systematic review across four dimensions: internal validity (search and selection), construct validity (classification and extraction), external validity (generalizability), and conclusion validity (synthesis and metrics). The assessment is based strictly on the documented audit trail of the review process.

7.1 Search coverage and publication bias

Threat. The primary threat to internal validity is the lack of systematic documentation for the original search strategy. As documented in the SLR Search Audit Report (§A.2), the only confirmed search activity with a verifiable timestamp is a DeepSeek export from 2026-10-12 containing 59 excluded records. No logs exist for database queries (e.g., Scopus, IEEE Xplore, Web of Science), search strings, result counts, or date filters for the initial identification phase. Consequently, the "upper half" of the PRISMA 2020 flow diagram (Identification → Screening → Retrieval) is reconstructed from author working files rather than observed from search-engine exports.

Effect. The review's coverage of the literature cannot be independently verified or reproduced. It is unknown whether relevant studies published in venues not surfaced by the specific (but undocumented) discovery route were missed. The potential for publication bias is substantial given the corpus's preprint skew (§7.8). The audit explicitly bars the claim that traditional databases were systematically searched: publication of a study in a database-indexed venue is not evidence that the database was searched.

Mitigation.

  • Completed: The Search Audit Report was produced to transparently map the available evidence and to explicitly flag every missing search-metadata item (search strings, per-database counts, dates, filters — audit List B, ten items). A Screening Register was retrospectively constructed assigning every record a unique ID (REC-001…REC-105), an exclusion code where applicable (EC-1…EC-6, covering all 59 excluded records) and a population tag, yielding an auditable list of what was screened even where the per-paper "Discovery route" column reads "NOT RECORDED".
  • Not performed: The supplementary search across Scopus, Web of Science, IEEE Xplore, ACM DL and arXiv proposed in the audit (§5.1, "Priority 🔴") has not been executed as of this draft. The review therefore relies on the corpus available at audit time; coverage-related findings should be read as descriptive of this specific, documentation-limited dataset.

7.2 Selection and screening bias

Threat. The screening process was not documented prospectively. The register records that reviewer identity, screening dates and the adjudication stage (title/abstract vs full text) were not recorded for the included records; there is no inter-rater agreement data. The 59 excluded and 46 included records derive from the author's workbooks, and for RQ1/RQ2 in particular the audit (§B.3) finds no exclusion records at all, with file naming (rq_1 find N.pdf) hinting at a discovery process whose method is unconfirmed.

Effect. Selection bias cannot be quantified. It is unknown whether inclusion reflects systematic screening or a corpus of "known" papers; if the latter, the evidence base over-represents the authors' immediate research circle and search-engine surface behaviour.

Mitigation.

  • Completed: The Screening Register and Study-Level Final Determinations table were constructed retrospectively and then adjudicated: the final determinations carry the column "FINAL full-text determination (author-accepted DP defaults 1A-6A, 2026-10-12)", meaning each record's status was re-checked against the author-approved default policy (six decision points covering grey literature, non-LLM infrastructure, non-embedded comparators, indirect-testing relevance, and cohort demarcation) rather than inherited silently. Zero records were excluded at the full-text stage; instead, 12 non-LLM studies were retained as demarcated Contextual/Comparator cohorts and 3 as Gray-zone, each with its counting rule recorded — this prevents scope creep while preserving transparency about the origin of every study.
  • Not performed: Independent double screening, reviewer calibration and inter-rater reliability statistics (e.g., Cohen's Kappa) were not performed and are not claimed.

7.3 Terminology variation and classification ambiguity

Threat. The included studies and the per-RQ extractions use inconsistent terminology for core constructs, threatening construct validity:

  • Simulator vs emulator: the RQ5 extraction codes "Simulator" 6/6 while RQ6 codes Simulator 0/6 for the same tooling (QEMU, Unicorn), classifying them strictly as emulators (cross-synthesis D-2; the RQ5 row label was truncated in parsing, so the discrepancy cannot be resolved from the files).
  • Mock: in RQ4, "mock" denotes a unit-test double in S05 (openSIL) but is the source paper's own verb for system-level vehicle-state simulation in S14 (P26).
  • Coverage: in RQ1, "test coverage" in study 2511.19132v1 means fault-scenario coverage, not code coverage.
  • Feedback: RQ7 separates evaluation-only measurement from refinement-loop input (S13's coverage is used as an evaluation index, not a loop, hence "Not reported" rather than "Yes").
  • HIL label ambiguity: one RQ4 study's HIL classification is ambiguous (D-9); excluding it would move RQ4's HIL and real-hardware prevalence from 33.3% to 16.7%.

Effect. Cross-study category counts are sensitive to classification rules; a zero count may reflect a strict definition rather than an empirical absence. Terminology-driven counts cannot be merged across RQs (e.g., no simulator figure may be pooled between RQ5 and RQ6 pending adjudication).

Mitigation.

  • Completed: The revised cross-RQ synthesis adopts a "preserve and report, never silently harmonize" policy: an eleven-entry Discrepancy Log (D-1…D-11) records every unresolved conflict with both sides and their source lines; Results, Discussion and Gaps sections quote each count within its own dataset's classification and flag terminology-dependence wherever a number is load-bearing; the type I / type II zero distinction (method-use zeros vs limitation-discussion zeros) constrains what any zero may be used to claim.
  • Not performed: No adjudication of these conflicts by a second coder; eight items remain formally pending author verification (V1–V8).

7.4 Missing or non-original full text

Threat. A significant portion of the "full text" evidence is derivative. The PRISMA audit concluded that for 22 of the 46 included records (covering all 14 studies of the RQ5–RQ8 cluster) the local PDFs are author-generated verification documents created 2026-10-08/09 via print-to-PDF pipelines — they share embedded-font signatures with known verification artifacts, and the "original PDF filename" values recorded for these rows do not exist on disk. Twenty-four records (RQ1–RQ4 folders) are confirmed publication originals.

Effect. Extraction for the 22 affected records relies on secondary artifacts rather than publisher-verified originals. If a verification document itself contains an error, downstream extraction inherits it without an independent anchor. Page references in these sources may be approximate.

Mitigation.

  • Completed: The distinction is recorded in the register ("Local full text resolved path"), disclosed in the Results data notes (N3) and in the PRISMA reporting ("consultation evidence" per study; 28/28 studies were demonstrably read at page level via quoted page/section citations). The verification documents contain per-item quotes, page/section positions and verification verdicts, so every extracted claim traces to a specific location in the artifact used.
  • Not performed: Re-retrieval of the publisher originals for the 22 derivative records, and re-verification of extracted claims against them.

7.5 Inconsistent study reporting and metric incompatibility

Threat. Primary studies report data inconsistently, and metrics are often incomparable:

  • Internal contradictions in sources: R2_p4's Top-1 appears as 60.73% and 60.75%; its query count as 3,208 and 1,700; R2_p7's success rates as 14%, 16% and 66% in different places; RQ1's source reports 88.65% vs 94.98%, and an accept/modify/rewrite split summing to 100.1% (D-8).
  • Metric heterogeneity: RQ8 records no common benchmark, baseline, quantified metric or evaluation environment (each 0/4), and states that studies sharing a metric name differ in definition and denominator, barring pooling; RQ1 records four mutually incompatible execution-accounting regimes and declares effect-size synthesis "impossible".
  • Extraction-side conflicts: RQ8's own summary table contains nine internal count conflicts on non-zero magnitudes (D-3), and some source tables were damaged in parsing (corrupted repeated values; a truncated RQ9 gap table), limiting per-study attribution (D-11).

Effect. Quantitative synthesis is impossible for most dimensions; prevalence claims are constrained by small denominators; load-bearing source figures carry multi-version uncertainty.

Mitigation.

  • Completed: Conflicts are preserved, logged and side-reported (D-3, D-8, D-11), never resolved by selection; the review's own Results use RQ8's verified classification tables (whose zero rows — the ones cited downstream — are unaffected by the nine non-zero conflicts); every percentage is bounded to its own denominator (Registry Table 4) and no cross-dataset pooling is performed anywhere; multi-version figures are quoted only with the preserved-contradiction caveat.
  • Not performed: Manual re-adjudication of the nine RQ8 conflicts and the damaged-table attributions against the source PDFs (scheduled as author action V5/V6, not yet done).

7.6 Multiple reports of the same study and deduplication

Threat. The 46 included records collapse to 28 unique studies: 18 records are cross-RQ re-loggings of studies already present in another RQ dataset, and one study (S26 LLMLOOP) has two reports (conference version plus preprint). The register annotated these clusters retrospectively; no prospective de-duplication log exists, and the PRISMA-side count "duplicate records removed: 0" reflects annotated re-loggings rather than a dedup run.

Effect. Without study-level collapsing, prevalence statistics would double-count studies appearing in several RQ datasets, inflating apparent evidence for overlapping dimensions.

Mitigation.

  • Completed: The Study-Level Final Determinations table assigns a unique Study ID (S01–S28) to every record cluster, with Records(n) summing exactly to 46; all study-level counts in Results de-duplicate by study, configuration-level counts retain all records, and the two levels are never mixed; the cross-RQ overlap matrix and the "reports = 29" audit (28 studies + 1 documented version pair) are built on this registry.
  • Not performed: Bibliographic fuzzy-duplicate detection across the screened 105 records (dedup was by normalized-title clustering within the register, recorded as such).

7.7 LLM-assisted extraction and synthesis errors

Threat. Extraction and synthesis for the verified datasets were performed with LLM assistance. LLMs can hallucinate, misread technical details, or collapse the distinction between "Not reported" and "No" — the exact failure that would fabricate gap claims from silence.

Effect. If uncorrected, extraction errors would propagate into every RQ count and therefore into the Discussion and Gaps sections.

Mitigation.

  • Completed: Each RQ report carries per-study verification tables and explicit coding rules ("Not reported", "Unclear", "No" kept distinct throughout); the RQ9 layer adds a second-order verification in which 4 of 75+4 extracted items were rejected and 23 of 75 retained items (30.7%) were downgraded by the verification files themselves — direct evidence that the check layer overrode first-pass coding; inference-based codings were struck (e.g., NVIC-capability mentions "removed as inference"); and prohibition rules from the files ("absence cannot be converted into a research gap", "'Out of scope' ≠ future work") are enforced at the claim level.
  • Not performed: Independent re-extraction of any record by a non-LLM second extractor, or a formal error-rate study of the extraction pipeline.

7.8 Limited generalizability

Threat. The corpus is small (28 studies; the LLM-construct population on which the review's core claims rest numbers 13), heavily preprinted (RQ2: 6/7 arXiv, 1 peer-reviewed venue; DOIs absent across most datasets; one included grey-literature thesis), and concentrated in two sub-communities (firmware fuzzing/re-hosting; automotive/HIL test generation). The review's headline construct — hardware-aware LLM test generation for embedded C — is instantiated end-to-end by no study in the corpus (RQ9 construct-validity finding).

Effect. Findings describe this verified dataset, not the field at large; generalizing to "how the literature does X" would be unsupported, and the preprint-heavy composition further weakens stability (unreviewed, potentially superseded results).

Mitigation.

  • Completed: Every RQ report's self-qualification against prevalence claims is quoted and obeyed (e.g., RQ5: "licenses no prevalence claim about the broader SLR population"); cohort demarcation (LLM-construct vs Contextual vs Comparator vs Gray-zone) fixes which population each statistic describes, and LLM-population statements use N = 13, never 28; all gap statements are worded as "unobserved within the verified dataset" with the search-scope caveat carried in the Gaps section (§6.8); the grey-literature thesis is used under a descriptive-only restriction.
  • Not performed: Snowballing or citation-chasing to test corpus completeness (proposed in the audit's logging templates; not executed).

7.9 Scope statement

The four threat classes above bound every claim in this review: search documentation gaps constrain coverage claims (§7.1–7.2); classification and artifact issues constrain construct claims (§7.3–7.4); reporting heterogeneity constrains conclusion claims (§7.5–7.6); extraction-assurance limits constrain error bounds on all counts (§7.7); and the dataset's size and composition constrain all generalization (§7.8). Where the records are silent on a procedural safeguard (registration, double screening, inter-rater agreement, sensitivity analysis), this section states that silence rather than implying the safeguard existed.

8. Conclusion

8.1 Purpose and method

This review set out to characterise, from verified primary evidence, how large language models are being used for hardware-aware test generation in embedded C — specifically what test types they produce, which strategies and contexts they use, how hardware and peripheral dependencies are handled, how interrupts, asynchronous behaviour and timing are addressed, where generated tests are executed and validated, which feedback loops refine them, how results are measured, and what limitations the literature itself acknowledges (RQ1–RQ9).

The review proceeded from a documented corpus of 105 screened records, of which 59 were excluded (56.2%) under six recorded exclusion codes and 46 were included (43.8%); the included records collapse to 28 unique studies corresponding to 29 reports. Cohorts were demarcated rather than merged: 13 LLM-construct studies (46.4%), 8 Contextual non-LLM (28.6%), 4 general-SE comparators (14.3%) and 3 Gray-zone (10.7%), with LLM-population statements always drawn from the 13-study cohort. Each research question was answered from its own independently verified extraction dataset (denominators 4, 7, 8, 6, 6, 6, 5 and 4 studies for RQ1–RQ8; 6 studies for the derived RQ9 analysis), and every percentage is valid only inside its own denominator. Where the primary sources conflict, the conflicts are reported side by side and adjudicated by neither this review nor its readers' convenience; where a category is empty, the emptiness is reported as "not observed within the verified dataset", never as absence from the literature. The identification stage of the search was reconstructed from author working files rather than observed from database exports, and this constraint is disclosed throughout.

8.2 Principal findings across RQ1–RQ8

Test types are bimodal, with the middle levels empty. Reported activity concentrates at unit level (2/4, 50.0%) and at HIL/system level (2/4, 50.0%); integration (0/4) and regression (0/4) are absent, and the two absences differ in kind — integration was explicitly ceded to mature SIL/MIL/PIL toolchains, while regression is total silence that supports no conclusion in either direction. Only one of four studies emits C-language test code (25.0%); the rest produce Python or JSON artefacts.

Strategy work is real but aimed at software artefacts. Zero-shot prompting is near-universal (6/7, 85.7%), RAG is common (5/7, 71.4%), agentic workflows appear in 4/7 (57.1%), generation-LLM fine-tuning in only 1/7 (14.3%), and chain-of-thought as an explicit technique in no configuration. All seven studies are multi-model; no single model is used by more than two studies. Reporting completeness is the strategy side's own weak point: model identity and prompting technique are each unreported in at least one configuration for 5/7 studies (71.4%).

"Hardware awareness" is currently a software-artefact concept. Software context reaches the model in 8/8 studies (100%), while any embedded-hardware context appears in 5/8 (62.5%), low-level hardware documentation in 3/8 (37.5%), datasheets at inference time in 2/8 (25.0%) and a formal peripheral specification in 1/8 (12.5%). Register maps, MCU specifications, board documentation, clock and memory-map configuration, electrical/interface, sensor/actuator, communication-protocol, interrupt, timer and DMA specifications are each confirmed as model input in 0/8 studies; HAL/driver/BSP/RTOS artefacts reach inference-time context in 0/8; and among the three studies whose LLM role is genuinely test generation, confirmed hardware context is 0/3 (0%). Execution feedback (compiler errors, build/flash logs, coverage, HIL action results) is present as context in 4/8 (50.0%) and functions, in the source's own terms, as a stand-in for hardware awareness.

Dependency handling is delegated, not generated. In 5/6 studies (83.3%) the LLM produces no dependency-handling artefact at all; instead 19/27 configurations (70.4%) have it generate hardware-related production code. The two handling families — provision (4/6, 66.7%) and replacement (2/6, 33.3%) — never intersect, and hybrid strategies number 0/6. Exactly one unambiguous positive cell exists: LLM-generated tests with stubs, executed on host. Behaviourally faithful doubles (register, timing, interrupt or protocol semantics) appear in 0 of 27 configurations, and quantitative simulator/emulator fidelity assessment appears nowhere in the dataset.

Interrupt semantics are modelled without LLMs; time is inherited, never controlled. Asynchronous and timeout-related behaviour are reported in 6/6 studies (100%), interrupts are present in 5/6 targets (83.3%), and ISR handling, interrupt injection, NVIC simulation, temporal assertions and delay handling each reach 4/6 (66.7%). Real-time property measurement is concentrated in a single study: WCET, jitter, deadline validation and race-condition testing are each 1/6 (16.7%), contributed by the same study, whose own interrupt handling is unreported. LLM-driven interrupt/asynchronous/timing test generation is 0/6; nested interrupts and interrupt priorities were tested by 0/6; fake or mock clocks, deterministic simulation-time mechanisms and clock-domain modelling are each 0/6. Time is a side effect of running an emulator in 5/6 studies, and although all six report timeout-related behaviour, firmware timeout is tested as a functional constraint in none. OS-level scheduling semantics are unmodelled (0/6 each for scheduler modelling, task switching, thread interleaving and message/event queues), which must be read alongside the non-zero concurrency counts (concurrency 2/6, explicit scheduling control 2/6, semaphore/lock/race each 1/6).

Execution is emulator-bound. Emulator, host, hybrid and software-only validation each apply to 6/6 studies (100%), with QEMU dominant in 5/6 (83.3%). Real hardware appears in 2/6 (33.3%) and only in secondary roles — bug confirmation and baseline comparison; HIL appears in 1/6 (16.7%), again only as a baseline, while five studies explicitly avoid HIL and market hardware-independence as a design goal. Real hardware is the primary execution environment in 0/6 studies; simulators (strict term) and virtual platforms are 0/6; and no study in the dataset reports the compilation of its generated tests.

Feedback loops are closed, but on software signals. Automatic closed-loop refinement is universal (5/5, 100%), with one-shot, manual, semi-automatic and mixed strategies at 0/5. Loops close on execution results (5/5), LLM-generated corrections (5/5), test failures (4/5, 80.0%), compiler errors (3/5, 60.0%) and coverage (3/5), while hardware/peripheral feedback reaches only 1/5 (20.0%) and sensor outputs none. Embedded firmware is the target in only 2/5 studies (40.0%), and neither embedded study reports an iteration budget.

Evaluation cannot arbitrate between these positions. Execution (4/4) and benchmark comparison (4/4) are universal; compilation, mutation testing, simulation/emulation and coverage analysis each appear in 2/4 (50.0%). Real hardware, HIL, fault seeding, fault exposure, human evaluation, expert review and statement/branch/function/condition coverage are each 0/4, as are common benchmarks, common baselines, common quantified metrics and identical evaluation environments; no study quantifies coverage and mutation score together. Two disjoint datasets independently record that the usual proxies dissociate: RQ1 finds four mutually incompatible execution-accounting regimes and no complete funnel, and RQ8 records that where a metric name recurs across studies its definition and denominator differ, which is why the source bars pooling. Within RQ1 the evidence also separates executability from test validity, and within RQ8 one study dropped coverage on the grounds that it is weakly correlated with fault detection. No study anywhere in the corpus reports a complete generated → compilable → executed → passed funnel, and quantitative meta-analysis is therefore impossible rather than merely unattempted.

The corpus is two clusters that do not meet. Of the 28 pairwise study-set overlaps, 14 are zero, 12 share 1–3 studies, and only 2 share four or more (RQ2×RQ3 = 6; RQ2×RQ4 = 4). The datasets carrying all strategy and context evidence share no study with those carrying all interrupt, environment, feedback and metric evidence, and the single documented bridge between the clusters rests on a feature-level identity match that remains pending verification. Consequently no study in the verified corpus is simultaneously LLM-based, test-generating, embedded-C-source-level and hardware-aware.

What the evidence does and does not license about LLM effectiveness. No overall verdict is supported, and this review offers none. The verified record is specific and bounded on both sides. On the positive side, all four RQ1 studies report executing their generated artefacts (4/4), RQ7 finds automatic closed-loop refinement universal (5/5, 100%) with quantified gains reported wherever iteration was measured, and RQ8 records execution-based validation in every study (4/4). On the negative side, the RQ1 sources use four mutually incompatible execution-accounting regimes and none reports a complete generated → compilable → executed → passed funnel; the single study that produced C test code for an RTOS codebase abandoned the effort, its output described as often unusable without extensive manual modification; and RQ8 finds no common benchmark, baseline, quantified metric or evaluation environment (each 0/4), so no study's result can be checked against another's. These statements describe particular configurations in particular datasets; neither the positives nor the negatives scale to a field-level claim that LLMs are, overall, effective or ineffective for hardware-aware embedded-C test generation.

8.3 Most important verified limitations and gaps (RQ9)

At study level (denominator 6; the 75 retained limitation instances are never used as prevalence, and one study alone contributes 13 of them, 17.3%, while counting once per category), the highest-support author-acknowledged limitations are: execution validation is present but never hardware-grounded, 5/6 (83.3%), reported alongside the narrower verified count that only 2/6 lack real-device evaluation as a confirmed gap, because one study did re-execute crash-inducing inputs on physical devices; and LLM capability is real but narrow and merely advisory, 5/6 (83.3%). Next is peripheral/interface dependence, 4/6 (66.7%) — the most consistently verified hardware gap across the RQ9-derived six-study limitation set (of which only two are corpus members, S17 and S13; the other four are RQ9-side works). At 3/6 (50.0%) each: the unresolved test-oracle problem, the only gap with a demonstrated empirical leak, in which a real bug fired under test and went undetected by the simple memory-error detector; timing behaviour unmodelled at key points, of which the strongest is the finding that neither the study nor existing fuzzers consider input duration, named by its authors as an open challenge; incomplete interrupt semantics; weak register/configuration-layer handling; missing or limited DMA support; human involvement not eliminated; and a platform and generalisability ceiling. At 2/6 (33.3%): limited RTOS/concurrency handling, and driver complexity — with HAL explicitly not established as a distinct verified limitation. Two single-study observations (1/6 each) are recorded as such and not generalised: functional correctness not implying security correctness, and closed-source model dependency.

Three features of this evidence limit how strongly any of it may be stated. Verification downgraded 23 of the 75 retained instances (30.7%) and rejected 4 outright; several apparently hardware-related items are inferences from silence rather than author statements; and a set of commonly assumed LLM weaknesses — hallucination, incorrect or invented APIs, named reasoning limitations — is discussed as a limitation by 0/6 studies, as are formal threats-to-validity sections, statistical analysis, HIL and HAL. Because these are silences in limitation discussion rather than absences of method use, they support no gap claim; what they do establish is that the verified LLM-side weaknesses in this literature are concrete and different from the field's usual assumptions — compilation failures attributed largely to missing context and to model logical inconsistency rather than to fabrication, LLM-as-a-judge verdicts unreliable across runs, independent generations converging on functionally correct designs with similar security weaknesses, and an LLM used only as a heuristic guide whose poor suggestions do not block exploration.

On the method-use side, the corpus exhaustively verifies as absent the combinations that a hardware-aware pipeline would need: LLM-generated tests executed on a simulator, emulator, HIL rig or real hardware (0 studies); LLM-built peripheral models, device drivers, HALs, wrappers or configured execution environments (0); behaviourally faithful doubles and quantitative fidelity assessment (0/27 and 0 respectively); LLM generation of interrupt, asynchronous or timing tests (0/6); and hardware specifications in model context (0/8 across eleven categories). Each of these is a statement about the verified dataset under this review's classification lens, and each carries the alternative explanations recorded in §6 — hardware independence as a marketed design goal, delegation to mature infrastructure as a deliberate engineering choice, artefact-based interrupt-model extraction as a preferred route rather than a fallback, and scope boundaries that bound a study's claims without bounding the construct's feasibility.

8.4 Implications for future research

The evidence points to a small number of directions, each traceable to a specific verified finding and each carrying its precondition.

First, produce studies that instantiate the whole construct. Because 14 of 28 pairwise overlaps are zero, only a study that simultaneously generates embedded-C tests with an LLM, supplies hardware-informed context, executes on a hardware-relevant substrate and reports a complete funnel can convert today's cross-dataset contrasts into within-study evidence. Reusing verified artefacts and rigs already in the corpus is the lowest-variance route, and the one documented C-level failure should size expectations toward assisted, human-gated authoring rather than autonomy.

Second, close the measurement gaps before the method gaps. A quantitative virtual-to-physical fidelity measure does not exist anywhere in the dataset, although fidelity is the dimension most consistently reported as a limitation and least consistently measured; without it, "hardware-aware" and "faithful" remain unfalsifiable. Likewise, a shared benchmark for embedded-C test generation must pin MCU family, toolchain versions, dependency infrastructure and the four-stage funnel definition, use code unseen during pretraining, and instrument coverage together with mutation or fault seeding so that the proxy dissociation recorded in two disjoint datasets becomes testable rather than anecdotal.

Third, put hardware semantics inside the loop. The verified machinery for interrupt modelling already exists in four studies and has never been pointed at LLM test generation; nested interrupts, priorities and ISR sequences are the named zeros. Time needs to become controllable — fake or mock clocks and deterministic simulation time — so that delay duration, periodic execution and timeout become tested properties instead of tool budgets, with terminology unified first, since six studies currently report "timeout" with six different referents. Context grounding should be tested as an explicit comparison: hardware specifications supplied at inference time versus extraction from the artefact versus training-time consolidation, with the possibility preserved that artefact extraction is the better route. Feedback loops, already saturated as a technique, need hardware-adjacent signals (register, MMIO/NVIC state, DMA events, timing measurements) and oracles distinguished at three layers — syntactic, functional and hardware-behavioural — while treating LLM-as-a-judge as a verified-unreliable candidate.

Fourth, do the zero-cost work first. Eight verification items remain pending, and one of them decides whether the two research clusters are connected at all; its failure would downgrade every cross-cluster statement in this review by one strength level. Resolving these before extending the corpus is the only improvement in evidential strength available without new literature.

Finally, three framings the evidence does not support and that future work should avoid: treating hallucination reduction as this field's bottleneck (the verified failure profile is context loss, logical inconsistency, judge instability and convergent weaknesses); claiming that the literature ignores HIL, HAL or RTOS (all type-II silences, with live HIL usage recorded elsewhere in the corpus); and justifying model-capacity work by prevalence statistics this corpus cannot lawfully produce.

8.5 Scope of these conclusions

Everything above is bounded by the review's own conditions of evidence. Counts describe datasets of 4 to 8 studies and an RQ9 denominator of 6, so single studies move percentages by 12.5 to 25 points and no prevalence claim about the wider literature is licensed. Every zero means "not observed within the verified dataset under this review's classification scheme"; the records show that the lens moves counts, with the same tooling coded as simulator in one dataset and emulator in another, "mock" naming both a unit double and a system-level simulation verb, "coverage" denoting fault-scenario coverage in one study, and "feedback" covering both evaluation-only measurement and refinement input. Search documentation is incomplete at the identification stage, terminology reach is bounded by the review's own vocabulary, 22 of 46 records rest on author-generated verification documents rather than publisher originals, and nine internal count conflicts in one dataset's summary remain unadjudicated. Within those bounds, the verified picture is coherent and specific: a field with mature generation machinery on the software side, mature hardware-modelling machinery on the infrastructure side, and no verified study yet connecting the two — a structure consistent with a pre-paradigm intersection rather than with a failing literature.

B.6 Quality assessment

No quality assessment was applied. No scoring of any included study exists in the project: there is no QA column in the register or the determinations table, and no scored rubric output anywhere in the project. What exists is a draft rubric held as a proposal only — dimensions QA1 to QA7: objective stated; LLM/approach stated; embedded context stated; test procedure stated; execution/validation setup stated; metrics reported; reproducibility detail — generated under an explicit instruction to label a proposed rubric as a proposal rather than as an already-used method. Two study-specific treatment facts substitute for quality gating where they matter: the grey-literature thesis (S04) is admitted under a descriptive-only restriction (DP-5A); and RQ8's own synthesis prohibits popularity claims because of its denominator (4 studies) and nine recorded intra-dataset count conflicts on non-zero magnitudes — a data-quality judgement embedded in the synthesis layer rather than in a QA instrument.
